This tab explains how the different logic programs of a game talk to each other: what each program gets as input, which parts of its answer set are kept, and where those parts go next. It describes what the game engine (js/engine.js) actually does. The Instructions tab gives the same picture in less detail.

The basic mechanism

The programs never call each other directly. All communication goes through plain text, handled by the game engine. Every time a program is used, the engine does the following:

  1. It glues together a number of pieces of text: some rules added by the engine itself, facts computed earlier (such as the current state of the game), and one or more of the programs from the Game rules and Strategy tabs. The pieces are concatenated in a fixed order, separated by newlines.
  2. It runs clingo on the result, with the options -n1 -Wnone --heuristic=Domain. Only the first answer set that clingo finds is used. (So a game is only random through RANDINT or #heuristic statements, not because clingo picks an answer set at random.)
  3. It filters the answer set: only atoms with certain predicate names are kept. For example, from the player's answer set only atoms over do, remember and forget are kept. Everything else (helper predicates and so on) is thrown away.
  4. It writes the kept atoms back as facts (a. b. c.), which become input text for the next program.

Between programs, the engine keeps the following pieces of text:

  • Level state: the at(R,C,O) facts of the initial state of the level (shown under Level state in the level editor).
  • Level settings: the setting(...) and decorate(...) facts of the level, which stay the same during the whole game.
  • Game state: the whole history of the game, as facts at_time(T,R,C,O), meaning that object O is in cell (R,C) at time T, and facts state_time(T), one for every time T so far. A new time slice is added at each step. Old slices are kept only if one of the programs that get the game state (visibility, nature, winning conditions, the auxiliary program, or the level settings) mentions at_time or state_time; otherwise only the latest slice is kept. This gives the same results, but is much faster: with the whole history, every program would ground all past steps again in every step. The state_time facts make it possible for a time slice to be empty (when there are no objects left).
  • Player input: the observe(...) and setting(...) facts that the player gets to see at the current step, and the fact current_time(T).
  • Decorations: the decorate(...) facts that are used to draw the grid at the current step.
  • Player memory: the memory(...) facts the player carries from one step to the next. It starts out empty.

Most programs do not work with at_time directly. Instead, the engine adds the following two rules, which pick out the latest time and present it as current_time(T), and the objects at that time as plain at(R,C,O) facts: 

current_time(T) :- T = #max { S : state_time(S) }.
at(R,C,O) :- at_time(T,R,C,O), current_time(T).

Below, these two rules are called the current-state rules.

Before the game: generating the level

When Generate level is pressed, the engine takes the level generation program, replaces every RANDINT(l,u) by a random number, and adds the auxiliary program. From the first answer set:

  • atoms over at (and debug) become the level state;
  • atoms over setting and decorate become the level settings.

If there is no answer set, both are left empty and there is no level to play.

When the game starts, the level state is turned into the initial game state by this small program: 

at_time(0,R,C,O) :- at(R,C,O).
state_time(0).
% ... followed by the level state

Only the at_time and state_time atoms are kept. So everything in the state of the game is a triple (R,C,O) at some time T; other atoms in the level state (such as debug) are dropped here.

One time step, in order

Right before the first step, the engine runs the visibility program once on the initial state, to get the first player input. Then every time step consists of the following, in this order:

  1. Winning conditions. The goal program is run on the current state. If it derives lose or win, the game ends here. This happens before the player moves, so in step 1 the initial state is checked as well.
  2. Engine timeout. If 500 steps have already been played, the engine stops the game with TIMEOUT!, which counts as a loss. This catches games that would otherwise go on forever.
  3. Drawing the grid. The grid is drawn from the player input, the decorations and the level settings. So the grid shows what the player sees, plus the decorations, not the true state of the game.
  4. Player strategy. The player program is run on the player input and the player's memory. This gives the moves (do) and the memory updates (remember, forget).
  5. Memory update. The memory updates are applied to the player's memory.
  6. Nature. The nature program is run on the current state and the player's moves. Its next atoms become the next time slice of the game state.
  7. Memory wipe. If nature derived wipe_player_memory, the player's memory is emptied. This happens after step 4, so whatever the player remembered in this step is lost too.
  8. Visibility. The visibility program is run on the new state, giving the player input and decorations for the next step.

The Game output in the Debug tab follows this order. For each step it shows the player input, the player's memory, the player's moves, the memory updates and the next state from nature. Whenever a program has no answer set or contains an error, the engine uses one of the fallbacks described below, and the game output says so (for example - Nature program: no answer set (state unchanged)).

Visibility

The visibility program sees the true state of the game, as at(R,C,O) (and, if it wants to, the full at_time history), plus the level settings. It decides what the player is allowed to know by deriving atoms over observe. The player input consists of these observe atoms together with all setting atoms (the latter come straight from the level settings, which are part of this program), and current_time(T) (from the current-state rules). So the player never gets raw at(R,C,O) facts: only observe(...), setting(...) and current_time(...).

The decorate atoms of this answer set are used only for drawing the grid. They include the decorate atoms from the level settings, because those are part of the program too. None of them are passed to the player.

Player strategy

The player program gets exactly four things: the player input (observe, setting and current_time facts), the player's memory (memory facts), the auxiliary program, and the player's own program (with RANDINT replaced anew in every step). It does not see the game state, the decorations, or the other programs. From its answer set, do atoms are passed to nature as facts, and remember/forget atoms are passed to the memory update.

Memory update

If the player derived at least one remember or forget atom, the engine computes the new memory as given by the following rules (it does so directly, without running clingo, because this is fast and cannot fail): 

new_memory(X) :- memory(X), not forget(X).
new_memory(X) :- remember(X).

The new_memory atoms are then renamed to memory, and these form the player's new memory. So remember wins over forget: an atom that is both remembered and forgotten in the same step is kept. A memory(...) atom that the player program derives itself (rather than gets as input) is not stored: only remember stores things.

Nature

Nature sees the true state, the player's moves as do(...) facts, and the level settings. From its answer set the engine keeps the next(R,C,O) atoms (and current_time(T)), and turns them into the next time slice as given by this program (again computed directly, without running clingo): 

at_time(T+1,R,C,O) :- next(R,C,O), current_time(T).
state_time(T+1) :- current_time(T).
% ... followed by the game state and the next atoms

Note that only next atoms survive: an object that has no next atom simply disappears from the game. This is why nature programs usually contain rules like next(R,C,flag) :- at(R,C,flag). If there are no next atoms at all, the new time slice is empty, but time still advances (thanks to the state_time rule).

If the nature program has no answer set (for instance because a constraint like :- do(X), do(Y), X != Y. is violated), the engine falls back to next(R,C,O) :- at(R,C,O).: time moves on but nothing changes. In that case the memory is not wiped.

Winning conditions

The goal program sees the current state, the level settings, and current_time(T), which is the number of steps taken so far (0 at the start). If its answer set contains any atom over lose, the game is lost. Otherwise, if it contains any atom over win, the game is won. Otherwise the game continues.

Worked example 1: Find the flag 1

Let's follow the first step of Find the flag 1 (with solution) on an 8x6 grid. The player starts in the top-left cell and the flag is at row 5, column 7. (The facts are shown one per line here. The engine writes them on one line, and their order may differ, but order does not matter.)

Level generation. The answer set of the level generation program gives the following level state and level settings: 

% Level state (atoms over at)
at(1,1,player).
at(5,7,flag).

% Level settings (atoms over setting and decorate)
setting(grid_width(8)).
setting(grid_height(6)).
setting(time_bound(15)).
setting(row(1)). setting(row(2)). ... setting(row(6)).
setting(col(1)). setting(col(2)). ... setting(col(8)).
decorate(game_type,grid).
decorate(label,flag,font_f024).
decorate(label,player,font_f007).

Initial state. The level state becomes time slice 0: 

at_time(0,1,1,player).
at_time(0,5,7,flag).
state_time(0).

Visibility. The visibility program (observe(at(R,C,O)) :- at(R,C,O).) is run on the current-state rules, the game state above, the level settings and the auxiliary program. The current-state rules derive current_time(0), at(1,1,player) and at(5,7,flag), and from there the visibility program derives the observe atoms. The player input is: 

observe(at(1,1,player)).
observe(at(5,7,flag)).
current_time(0).
setting(grid_width(8)).
setting(grid_height(6)).
setting(time_bound(15)).
setting(row(1)). ... setting(row(6)).
setting(col(1)). ... setting(col(8)).

and the decorations are the three decorate facts of the level settings.

Step 1, winning conditions. The goal program sees current_time(0), at(1,1,player) and at(5,7,flag). Neither win nor lose(timeout) is derived, so the game continues.

Step 1, player strategy. The player program is run on the player input above, the (empty) memory, the auxiliary program and the player strategy: 

do(move(down)) :- observe(at(R1,C1,player)), observe(at(R2,C2,flag)), R1 < R2.
do(move(right)) :- observe(at(R,C1,player)), observe(at(R,C2,flag)), C1 < C2.

Since the player is in row 1 and the flag in row 5, the answer set contains do(move(down)). This is the only atom that is kept. There are no remember or forget atoms, so the memory stays empty. The player's moves are: 

do(move(down)).

Step 1, nature. The nature program is run on the current-state rules, the game state, the fact do(move(down))., the level settings and the auxiliary program. The kept atoms are: 

current_time(0).
next(2,1,player).
next(5,7,flag).

These are turned into time slice 1 and added to the game state, which now reads: 

at_time(0,1,1,player).
at_time(0,5,7,flag).
at_time(1,2,1,player).
at_time(1,5,7,flag).
state_time(0).
state_time(1).

Step 1, visibility. The current-state rules now derive current_time(1), at(2,1,player) and at(5,7,flag); the old slice 0 is still in the game state but no longer counts as at. The player input for step 2 is: 

observe(at(2,1,player)).
observe(at(5,7,flag)).
current_time(1).
setting(grid_width(8)).
% ... and the other setting facts, as before

The rest of the game. The same cycle repeats. The player moves down until it reaches row 5 (after step 4), and then moves right. After step 10 the game state has slices 0 to 10, with at_time(10,5,7,player) and at_time(10,5,7,flag) in the last one. At the start of step 11, the goal program sees current_time(10), at(5,7,player) and at(5,7,flag), so it derives win, and the game is won. (The time bound of 15 is not reached, so lose(timeout) is not derived.)

Worked example 2: fog and memory

The first example has no hidden information and no memory. This second example is a small made-up game on a 1x4 grid: the player starts in cell (1,1), there is an item amnesia in cell (1,3), and the flag is in cell (1,4). The auxiliary, nature and winning conditions programs are those of Find the flag 1, with two extra rules in the nature program: 

next(R,C,amnesia) :- at(R,C,amnesia).
% Stepping onto amnesia wipes the player's memory
wipe_player_memory :- next(R,C,player), at(R,C,amnesia).

The visibility program only lets the player see its own cell and the cells next to it: 

observe(fog(R,C)) :- cell(R,C), at(R2,C2,player), |C-C2| >= 2.
observe(at(R,C,O)) :- at(R,C,O), not observe(fog(R,C)).

The player always moves right, counts its steps in memory, and remembers where the flag is once it has seen it: 

remember(steps(1)) :- not memory(steps(_)).
forget(steps(N)) :- memory(steps(N)).
remember(steps(N+1)) :- memory(steps(N)).
remember(flag_at(R,C)) :- observe(at(R,C,flag)).
do(move(right)).

Step 1. The player is in (1,1), so cells (1,3) and (1,4) are covered by fog. The amnesia item and the flag are not observed. The player input is: 

observe(at(1,1,player)).
observe(fog(1,3)).
observe(fog(1,4)).
current_time(0).
% ... plus the setting facts

The memory is empty, so the player derives remember(steps(1)) (and do(move(right))). The memory update turns this into the new memory memory(steps(1)). Nature moves the player to (1,2).

Step 2. From (1,2), the amnesia item in (1,3) can be seen, but the flag in (1,4) is still covered by fog. The player gets: 

observe(at(1,2,player)).
observe(at(1,3,amnesia)).
observe(fog(1,4)).
current_time(1).
% ... plus the setting facts

memory(steps(1)).

The memory updates are forget(steps(1)) and remember(steps(2)), which gives the new memory memory(steps(2)). But nature moves the player onto the amnesia item, so its answer set contains wipe_player_memory, and the memory is emptied. The steps(2) that was just remembered is lost too.

Step 3. The player is in (1,3) and can now see the flag. Its memory is empty, so it starts counting again from 1: 

% Player input
observe(at(1,3,player)).
observe(at(1,3,amnesia)).
observe(at(1,4,flag)).
observe(fog(1,1)).
current_time(2).
% ... plus the setting facts

% Memory updates derived by the player
remember(steps(1)).
remember(flag_at(1,4)).

% New memory
memory(steps(1)).
memory(flag_at(1,4)).

Nature moves the player to (1,4). At the start of step 4, the goal program derives win.

Appendix: notes

Some behaviour of the engine that is easy to miss. Most of these points are also mentioned in the Instructions tab.

  • The player gets observe, not at. The player gets the observe(...) atoms from the visibility program, the setting(...) atoms, current_time(...), its memory(...), and the auxiliary program, but never the state of the game itself.
  • lose takes precedence over win. The engine checks lose first, so if both are derived, the game is lost.
  • The history is available when it is used. A visibility, nature or goal program that mentions at_time or state_time gets all at_time facts since time 0, and can look at earlier states (the history then grows with every step, so each step's programs get a little larger). Otherwise only the latest time slice is kept (see Game state above).
  • Only at/3 is game state. Anything nature derives other than next (and wipe_player_memory) is lost. Any information that should last has to be encoded as an object in a cell.
  • RANDINT is only replaced in some programs: level generation, player strategy and nature. It is not replaced in the visibility, winning conditions or auxiliary programs.
  • Nature without next atoms empties the board. If the nature program has an answer set but derives no next atoms, the fallback is not used, and the new time slice is empty. Time still advances, because the game state also records state_time(T) for every time T. (The fallback that keeps everything in place is only used when the nature program has no answer set.)
  • Level generation leftovers. debug atoms from level generation end up in the level state, but are dropped when the initial state is made. The decorate atoms from level generation are part of the level settings, so the visibility, nature and goal programs can see them (the player cannot).
  • Memory details. If an atom is both remembered and forgotten in the same step, it is kept. If the player derives no remember or forget atoms at all, the memory update is skipped and the memory stays as it is.
  • Win/lose timing. Win and lose are checked at the start of each step, before the player moves, so an initial state that already satisfies the winning conditions is won in step 1.
  • Time limit. clingo runs in the background (in a web worker), so the page stays responsive. If a single call to clingo takes longer than 10 seconds (for example, because a program grounds to something infinite), clingo is stopped and the game ends with STOPPED!. The Stop button also stops clingo. The limit can be changed in the Options of the Control tab, or in the URL, e.g. ?timeout=30.
  • Time. The game output says, for every step, how long clingo took for each program (Time in clingo), and it adds a note when a program took more than 2 seconds in a step. Slow programs usually have rules with large groundings.
  • Errors. When clingo reports an error, the engine works out which program (and which line) it is in, and marks it in that program's editor. Programs are also checked for syntax errors and unsafe variables while you type.
  • No answer set. When a program has no answer set, the engine looks for the constraints (:- ...) in the programs that are violated: it runs clingo once more, with the constraints turned into rules, looking for an answer set that violates as few of them as possible. These constraints are named in the game output and marked in the editors.
  • Warnings about special predicates. While you type, the programs are also compared with what the engine gives them and takes from them (the table above). For example, there is a warning when the player's program never derives do/1, uses at/3 (which it does not get), derives a misspelled remeber/1, or derives moves that nature's program never looks at. These warnings come from a simple analysis of the program text (js/hints.js), so they are hints: clingo does not consider these errors.
  • No stratification check. Player programs are not restricted. (Earlier versions had an unused check that the player program is stratified and "simple", using stored/stratified.lp; the program is kept for reference.)
